# UAT report: rules R1 to R8

## Scope
User acceptance testing of the rule logic in `sql/10_features_and_flags.sql` (R1 to R7) and
`sql/15_r8_risk_list.sql` (R8, using risk list v1). The cases test rule version v2: see
"Version change to v2" below.

Out of scope:
- data loading (covered by the DQ checks in `sql/02_dq_checks.sql`)
- rule performance on real data (covered by the tuning and PVT reports)

## Approach
- Each case is a small set of hand-written transactions in `tests/uat_cases.csv`, sharing a
  `test_id`.
- Exactly one row per case is the target (`is_target = 1`) and carries the expected result
  (`expected_hit`).
- For each case, the rows are loaded as the table `txn`, `sql/10` is run unchanged, and the
  rule's flag on the target row is compared with the expected value.
- No Kaggle data is used, so the suite runs anywhere.
- A flag that comes back NULL fails the case. Every flag must be strictly true or false.

| Item | Value |
|---|---|
| Cases | 50 across 8 rules (R1 8, R2 4, R3 8, R4 8, R5 3, R6 5, R7 10, R8 4) |
| Transaction rows | 220 |
| Case types | below / at / above threshold, window start and end, midnight wrap, duplicate timestamps, no history (card's first-ever transaction), other cards' rows |
| How to run | `.venv\Scripts\python.exe -m pytest tests` (pass/fail) or `.venv\Scripts\python.exe src/run_uat.py` (refreshes the table below) |
| Environment | Python 3.12.10, DuckDB 2.0.0, Windows 11 |

Fields the rules don't read (city, state, zip, city_pop, unix_time) get fixed neutral values
in `src/uat.py`. Every case uses `is_fraud = 0`, because the rules never read the label.

## Ordering convention for same-second transactions
- Several cases depend on how rows at the same second are ordered.
- The convention is the one a streaming engine would apply: rows are processed in
  `(ts, trans_num)` order, and a transaction's features only include rows processed before it
  plus itself.
- R2 and R6 already used this order through `ROWS` windows. R1 and R7 did not; see the
  defect log.

## Version change to v2
When the tuned v2 thresholds were applied (see `reports/tuning_report.md`), the existing
suite failed 10 cases plus one structural check:
- **The 10 cases:** UAT-R3-02/04/06, UAT-R4-01/04, UAT-R6-01, UAT-R7-01/04/08/10.
- **The structural check:** R8 had fewer than 3 cases.

Evidence: [uat_evidence/pytest_v2_before_case_update.txt](uat_evidence/pytest_v2_before_case_update.txt).

Every failure was a boundary case that encoded a v1 threshold, which is what the suite is
for: no threshold changed without a test noticing. The cases were then rewritten for the v2
thresholds. Retired rules (R1, R2, R5) keep their cases, because their logic is still
computed for monitoring.

| Rule | v2 change | Cases updated or added |
|---|---|---|
| R3 | amt > 500 to amt > 600 | R3-02, R3-04, R3-05, R3-06 updated; R3-07 (exactly 600.00 at 03:59, no alert) and R3-08 (700 at 21:59) added. **UAT-R3-02 was written for v1** ($600.00 at 22:00 alerts, a brief requirement) **and is superseded in v2**, where $600.00 is not above the threshold. It now tests $600.01 at 22:00. The $600.00 no-alert behaviour is covered by R3-07, and by R3-01 at 21:59. R3-01 and R3-03 are unchanged and still pass. |
| R4 | grocery_pos 300 to 250; other three 500 to 600 | R4-01 to R4-04 moved to the new boundaries; R4-07 (misc_net) and R4-08 (shopping_pos) added |
| R6 | amount 300 to 750 | R6-01, R6-02 moved to 750.01 / 750.00 |
| R7 | 24 h, 3x to 48 h, 5x (two days of baseline) | All 10 cases rebuilt for the 48 h window and a threshold of 100.00 on a 10.00 baseline |
| R8 | new (list v1) | R8-01 to R8-04 added |

## Defect log

| ID | Rule | Found by | Severity | Description | Fix | Retest |
|---|---|---|---|---|---|---|
| DEF-01 | R1 (v1.0 to v1.1) | UAT-R1-06 | Medium | `txn_count_60m` used `RANGE ... AND CURRENT ROW`. RANGE treats every row at the same second as a peer of the current row, so a transaction's count included same-second transactions that come after it. The 4th of 5 same-second transactions got a count of 5 and fired; expected 4 and no alert. This breaks the rule that windows end at the current row, and it would not match a streaming engine (Phase 7 reconciliation). | Added `EXCLUDE TIES` to the RANGE frame, which removes all same-second peers, and added back only the earlier peers with a `ROWS ... 1 PRECEDING` count partitioned by (card_id, ts) and ordered by trans_num. | UAT-R1-06 and UAT-R1-07 pass |
| DEF-02 | R7 (v1.0 to v1.1) | UAT-R7-09 | Medium | Same cause as DEF-01, in `spend_24h`. The first of two same-second $20 transactions saw 24-hour spend of $40 instead of $20 and fired; expected no alert. | Same pattern as DEF-01, with SUM. | UAT-R7-09 and UAT-R7-10 pass |

Evidence:
- Before the fix, the suite reported `2 failed, 43 passed`: UAT-R1-06 and UAT-R7-09. See
  [uat_evidence/pytest_before_fix.txt](uat_evidence/pytest_before_fix.txt), the last five
  lines of the failing run. After the fix, all 45 tests passed: 42 cases plus 3 structural
  checks.
- **Impact on real data:** train has 20 card/second pairs with two transactions (40 rows) and
  test has 24 pairs (48 rows), none of them fraud.
  - On train, the fix changed `txn_count_60m` and `spend_24h` on 20 rows, the earlier row of
    each pair.
  - It changed no flag. `rule_performance.csv` and `value_detection.csv` on train are
    identical before and after.
- **Why it still matters:** it is a correctness issue that would show up as a mismatch in the
  Phase 7 engine reconciliation. It would also become material in a feed that sends
  duplicate submissions or batched timestamps.

## Known gaps (accepted, not defects)

| Rule | Gap | Evidence | Handling |
|---|---|---|---|
| R2 | A card's first-ever transaction can never fire, because there is no average to compare against. | UAT-R2-01. In train, 75 of 762 compromised cards had fraud as their first transaction. | Documented. Other rules (R3, R4) cover first transactions. |
| R6, R7 | A card's first-ever transaction can't fire, by design (R6 needs 10 prior transactions, R7 needs 7 prior active days). | UAT-R6-05, UAT-R7-07 | Documented. Same as R2. |
| R1, R2, R6, R7 | When two transactions share a second, which one is "first" depends on trans_num, which is a random identifier, not arrival order. | UAT-R1-06/07, UAT-R7-09/10 | Accepted. Results are deterministic, and the source data has no finer timestamp to order by. |
| R1, R2, R6, R7 | Production systems order same-second events by an arrival sequence number assigned by the authorisation switch. This dataset has no such field, so trans_num, a random ID, stands in for it. A live deployment must order by the sequence number. | Data dictionary: no sequence field in either file | Accepted for this project. Mapping ts plus a sequence number to the ordering key is a go-live requirement. |
| R7 | The 48-hour spend window is rolling, but the baseline is per calendar day, so recent spend from the previous days counts in both. | UAT-R7-08 | Accepted. v2 compares 48 hours with two days of baseline, which reduces the effect. |
| R8 | Merchant names must match exactly (case-sensitive). A production list would key on a merchant ID. | UAT-R8-04 | Accepted for this dataset, which has no merchant ID. |
